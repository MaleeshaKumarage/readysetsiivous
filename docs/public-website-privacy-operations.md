# Public website: privacy operations and evidence

This is an operator procedure, not a statement that every action is automated. Tenant administration owns the customer-request queue. The public contact route is info@readysetsiivous.fi. Keep request evidence in restricted business records, not in public GitHub issues.

## Access, correction and erasure requests

1. Record the received date, requested right, responsible administrator and response deadline (normally one month). Acknowledge receipt; assess any lawful extension before the deadline.
2. Verify identity proportionately using existing contact channels. Do not request identity documents by default. A booking number alone is not authority; use the private management key or independently verified identity. Never ask someone to post their key in an issue or public message.
3. Inventory records across bookings/customer contacts, messages, leads and attachments, account provider, reports, invoices, agreements, backups and relevant processors. Apply tenant boundaries and distinguish the requester from other people in shared records.
4. Record the legal/purpose basis for each retention decision. Do not delete invoices, signed agreements or evidence merely because a request arrived; retain only what applicable obligations or claims require, with restricted access and a documented end/review condition. Obtain legal/accounting advice where necessary.
5. Correct, erase, anonymise or restrict eligible records through authorized operations. Track processor notifications and copies. Do not promise that a user-facing deactivation is erasure. Define how restored backups reapply approved deletions and how immutable backups age out.
6. Respond securely with the outcome, any lawful refusal/restriction and complaint route. Never email unrelated customers' records or publish exports. Retain a minimal record of the request and outcome under an appropriate basis.

## Retention inventory to approve

| Category | Known processing | Required owner decision/evidence |
|---|---|---|
| Quotes/messages | Visitor explicitly sends a WhatsApp/email enquiry | Enquiry closure and deletion criteria; external-provider arrangements and access controls. |
| Bookings/contact/address | API persists the booking and its service/price snapshot | Operational retention, accounting/claim exceptions, deletion/anonymisation method. |
| Browser preferences | Language/theme saved on explicit selection; no automatic initial writes | Visitor can clear browser storage; no analytics purpose. |
| Authentication | Keycloak account and necessary session/security processing | Staff/account notice, retention, access and provider roles; outside this public booking change. |
| Reports/photos/voice notes | Existing business features may process personal data | Separate purpose/access/retention and sharing-link policies; do not assume public website copy covers staff monitoring. |
| Invoices/agreements | Legal/business records | Applicable statutory periods and legal holds, confirmed by the business/accountant. |
| Backups/security logs | Operational recovery/security | Actual schedules, regions, access, deletion replay and minimised logging evidence. |

No arbitrary retention durations or automatic purge jobs were introduced. Approve actual schedules before making precise public promises.
