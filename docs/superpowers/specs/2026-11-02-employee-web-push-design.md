# Employee PWA push notifications

## Outcome and scope

Extend the existing employee PWA on iPhone and Android with opt-in Web Push. Reuse current login, tenant boundaries, My shifts, effective shift/visit assignments and work records. Add no location permission, geofencing, clock restrictions, native app or email/SMS channel. Existing partner and lead emails continue unchanged.

Recommended initial alerts: a new assignment; a schedule/assignment change or cancellation affecting the employee; a reminder 30 minutes before a scheduled shift; and a reminder 30 minutes after scheduled end when that employee has started but has not ended/submitted the task. The timings are defaults included in this design for user review. Do not alert on unaccepted partner offers: only accepted assigned work participates. Send one assignment/change alert per employee per committed change, rather than one alert for every recurrence.

Use standards-based Web Push directly from the existing backend. This keeps account ownership and scheduling in the same system. A hosted push platform is an alternative but adds another service and processor without removing iPhone installation/permission requirements; do not introduce one in this increment.

## Employee experience and installation

Add a Notifications panel on My shifts and an account-page link to it. Show Enable notifications, current device status, Send test notification and Disable on this device. Support multiple enrolled devices; disabling one device does not disable the employee's other devices. Never request permission on page load. Request permission and subscribe only after the employee taps Enable. Test sends only to the current authenticated employee's current device and is rate-limited. Report provider acceptance accurately: it is not proof that the employee saw an alert.

Feature-detect service workers, PushManager and Notification. Show useful states for unsupported browser, blocked permission, unconfigured server, registration failure, enabled, and expired subscription. Denied permission gets settings instructions; do not repeatedly prompt. On iPhone/iPad require iOS/iPadOS 16.4+ and the installed Home Screen app, with installation guidance before enabling notifications. Android supports compatible browsers; offer installation for a consistent employee experience.

The current manifest starts the admin app. Add an employee manifest with a stable distinct ID, employee name, existing brand icons, standalone display and /me/shifts/ start URL, selected through /me route metadata. Preserve the admin manifest and admin install behavior. Adapt installation copy for employees rather than labelling their app Admin. Register the existing root /sw.js from the employee flow; retain its existing fetch behavior.

Notifications use short English system text, matching the current employee workspace. Do not include customer names, addresses, employee names, checklist content or photos in lock-screen payloads. Example: ReadySetSiivous — Your work schedule has changed. Open My shifts for the latest details. Upcoming and unfinished messages state their purpose without customer details. Push click focuses/opens /me/shifts/ on the current origin; the normal authenticated API supplies current task details. No arbitrary remote navigation URLs are accepted.

## Subscription ownership and APIs

Create tenant-scoped PushDevice records with ID, verified employee ID and auth subject, endpoint and browser encryption keys, VAPID public-key identifier, created/updated timestamps and enabled state. Endpoint/key values are confidential delivery credentials: no logs, browser analytics, admin employee DTOs or diagnostic dumps contain them. Limit enrollment to ten devices per employee and bound all strings and key lengths.

Add authenticated self-service routes under /api/v1/me/notifications: GET config/status (supported server configuration and public VAPID key only), PUT subscription, DELETE subscription/{id}, POST subscription/{id}/test. Resolve the actor with the same verified linked active employee rules as MeController, including identity-sync and work-role checks. Admins/managers may opt in only as their own eligible employee identity; partner-only accounts cannot subscribe as employees. Never accept a caller-selected employee/tenant or allow another employee's device to be read, deleted or tested. Return only safe status/device IDs, never another endpoint's credentials. Cross-tenant IDs are inaccessible. Apply no-store and request/rate limits.

Require a valid HTTPS push-provider endpoint with no userinfo/fragment and default HTTPS port. Restrict hosts to the supported browser push providers (Google FCM, Apple *.push.apple.com with label-boundary matching, Mozilla's known push endpoint); reject localhost, IP literals, custom URLs and redirects. Validate base64url P-256 public key and auth-secret lengths before persistence. The transport also validates the endpoint and disables redirects so stored input cannot become an SSRF proxy.

Never silently reuse a browser subscription after switching tenant/login. Keep a local binding marker scoped to the authenticated tenant/subject; unsubscribe and create a fresh browser subscription on a binding change. If the server reports a subscription belongs to another identity in the tenant, the UI also recreates it rather than transferring ownership. Remove the current authenticated server subscription before normal logout, attempt browser unsubscribe, and surface cleanup failures. Generic payloads and authenticated navigation limit stale-device disclosure. Worker delivery always checks current active employee/subject binding and subscription state.

## Scheduling and reliable delivery

Separate subscription management, event scheduling, persisted delivery intents and encrypted transport behind small application interfaces. Persist notification intents and per-device deliveries; stable event/device IDs make worker retries deduplicate locally. Database acceptance does not imply display or reading. Web Push has no universal exactly-once delivery guarantee: preserve stable notification tags to replace duplicate visible alerts and do not promise exactly-once transport.

Assignment/change intents must commit in the same tenant session as the scheduling mutation. Cover recurring assignment add/remove/date changes, shift schedule/name/branch changes, deactivation/deletion, moved/cancelled/extra visits, one-visit roster overrides, and accepted/cancelled partner work. Use explicit outbox staging in the existing shift repository mutation paths and the direct partner/visit mutation paths that bypass it; no sending within scheduling transactions. A failed scheduling write leaves no sendable intent. Include both previous and current affected employees for removal/cancellation messages, but never broadcast all employees. Coalesce changes still pending within the worker interval per affected employee/shift; only the current schedule is linked.

A minute-based background worker scans active tenants in fresh tenant-scoped services, following PartnerNotificationWorker. It materializes upcoming and running-task reminders using the existing effective occurrence/roster resolver and QC work evidence; do not use GetMyShiftsQuery as an eligibility source without filtering its retained personal-history rows. UTC timestamps and tenant-zone schedule resolution handle overnight visits and DST. Recurring reminders are keyed by shift/occurrence, employee and reminder kind. A moved occurrence supersedes the old reminder. Exclude cancelled/inactive/deleted shifts and ineligible employees; suppress upcoming alerts after start or when already started/completed, and suppress unfinished alerts after end/submission.

Only opted-in employees participate. Enabling the feature or a device must not backfill historic assignments or overdue alerts. Upcoming reminders may catch up after a short worker outage until scheduled start. Unfinished reminders are eligible for 60 minutes after their due time, once per employee/occurrence; older overdue reminders expire. No alerts are sent merely because an employee installs the PWA. Additional devices enrolled later do not receive previously queued events. Recheck eligibility and the effective visit immediately before delivery; assignment-removal notices use the committed prior-recipient fact and generic payload, not a current-assignment requirement.

Use a cross-replica nonblocking per-delivery reservation with bounded batches so the worker does not monopolize scheduling locks or send duplicates concurrently. Do not hold the tenant scheduling reservation across provider HTTP. Mark provider-accepted deliveries; retry network/429/5xx failures with bounded backoff and Retry-After, at most five attempts within event expiry. Treat 404/410 as expired subscription and disable that device. Permanent provider rejection is a recorded failure; ambiguous network acceptance may be retried with the same tag. Sanitize errors and never persist raw provider bodies or secret URLs. Before retrying, recheck cancellation, employee eligibility, disable state and expiry.

## Configuration and rollout

Use a maintained .NET standards-based Web Push library for VAPID and payload encryption instead of implementing cryptography. Keep the private VAPID key and subject in protected server configuration; expose only the public key. Validate the key pair at startup/configuration check. Default the sender to disabled when configuration is absent or invalid, and show Notifications unavailable rather than a misleading enabled state. Provide a local key-generation/setup command and deployment documentation; never commit or print a private key in tool logs or CI artifacts. Use stable persistent keys across restarts; key rotation requires reenrollment and clear UI handling.

Wire public enable/config status, the worker enable flag, VAPID key pair and subject through the existing protected deployment environment without changing Keycloak, employee roles or existing notification credentials. No bulk opt-in and no mass test delivery. Production activation requires the normal reviewed release/configuration flow. Users explicitly opt in on each device after release. Keep actual iPhone and Android receipt verification separate from mocked browser success; do not claim physical-device delivery until tested.

## Verification

Backend tests: linked identity and role denial; device ownership/tenant isolation; invalid/oversized endpoint/key input and SSRF/redirect rejection; opt-in/out and test rate limits; transactional scheduling outbox; every recurring/visit/partner change path; exact reminder timing, UTC/DST/overnight resolution, former assignees and cancelled/completed suppression; no history flood; two replicas, stable delivery IDs and retry/expiry; 404/410 cleanup; invalid/unconfigured VAPID state; no endpoint/key leaks in responses or logs. Use isolated PostgreSQL for atomicity and concurrent-worker tests.

Browser tests on desktop/mobile: no automatic permission prompt; enable/denied/unavailable states; iOS Home Screen instructions; subscription creation and registration/server failure recovery; send-test acceptance feedback; per-device disable; logout/account switching; employee manifest and unchanged admin manifest. Exercise service-worker push parsing, malformed payload fallback and same-origin click handling, including a closed-window case. Regress employee shift start/end/checklists and existing partner/lead notifications. Run type checks, production export and required CI. Verify real installation, permission, locked-screen receipt, click/login navigation and disable behavior on a physical iPhone and Android phone during rollout.
