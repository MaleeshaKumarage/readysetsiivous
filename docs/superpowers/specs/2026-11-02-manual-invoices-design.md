# Manual company invoices

## Approved outcome

Add a Manual invoice option on the existing admin Invoices page for separately agreed services or goods. Select a company from the existing dropdown and enter rows containing description, quantity (pieces), and unit price before VAT. Add and remove rows. Reuse saved issuer address, banking information, payment terms, configured VAT, invoice numbering, payment references, language options, PDF layout, and paid/void actions. Manual invoices appear in the existing list. No shift selection or billing period is required. No invoice email is sent automatically.

## Page behavior

Keep shift and partner invoicing intact. Introduce a selector for Shift invoice versus Manual invoice; partner-month remains within shift mode. Company, customer billing address, language, issuer settings, preview, issue, and invoice history remain shared. Customer billing address uses the existing editable address fields; do not invent an address from the company's branches. Start manual mode with one blank description, quantity 1, and blank price. Each row has accessible labels and a Remove button; retain at least one row. Add row appends the same defaults. Use a responsive stacked layout on small screens.

Display the saved default VAT rate in manual mode; changes to that rate remain in existing issuer settings. Preview shows per-row amounts and invoice net, VAT and gross totals calculated by the server. Prices mean net EUR unit prices. Any change to mode, company, address, language, rows or issuer settings invalidates preview. Ignore late preview responses after edits or mode changes. Issue is enabled only for the current preview; disable repeated submissions while pending. Preserve input after validation or network errors. Refresh history after successful issue and clear preview. A separate successful new manual invoice gets a new submission identifier; retrying the same submission must never create another invoice.

## Service and API boundaries

Add an application ManualInvoiceService with preview and issue methods and register it alongside ShiftInvoiceService. Add admin-only POST /api/v1/admin/invoices/manual-preview and POST /api/v1/admin/invoices/manual endpoints. Request fields: companyId, billingAddress, language, lines (description, quantity, unitPriceNet), submissionId (nonempty UUID), and previewToken for issuing. Responses reuse the existing invoice DTO plus previewToken for preview. Never accept client-calculated VAT, totals, issuer snapshots, invoice numbers or payment references.

Look up company and issuer through existing tenant-scoped repositories. Snapshot company identity/contact/business ID, supplied customer billing address and issuer data into the existing Invoice document. Manual invoices have CompanyId but no BookingId, shift IDs or period. Add nullable ManualSubmissionId to Invoice for retry identity; legacy records deserialize unchanged. Preserve PDF rendering, invoice list and mark-paid/void routes.

Preview validates and calculates without saving or allocating a number. Build a deterministic token from normalized inputs, submission ID, company/issuer snapshots, tenant-local issue date and calculated output. Issue acquires the existing cross-replica IShiftWorkReservation, checks for an invoice with that submission ID in this tenant, rebuilds and validates the token, validates issuer/payment details as shift issuance does, allocates the existing yearly invoice number and payment reference, and persists the immutable snapshot. Number allocation and invoice save use the existing shared session transaction. Keep any shared validation extraction narrowly scoped; preserve shift behavior.

Retry handling under the reservation: if the submission ID already exists with the same normalized manual request (company, billing address, language and ordered row inputs), return that invoice, even if paid or voided, without allocating another number or changing status. If reused with different inputs return 409. Persist a normalized request fingerprint with the invoice so retries can be compared independently of later issuer/company changes. Retry lookup occurs before recalculating current snapshots. A new submission ID intentionally permits another invoice with identical rows, since recurring separately agreed charges are valid. Never apply shift-period duplicate checks to manual invoices.

Add a tenant-scoped GetByManualSubmissionIdAsync repository method and nullable ManualRequestFingerprint on Invoice. Unlinked BookingId uses the existing Guid.Empty convention. Preserve submission ID for unchanged retries, including a lost success response. Disable edits while issuing. If an issue response is uncertain, retain that submission and offer retry/history reconciliation before allowing a deliberately new request; do not silently rotate the ID and risk billing twice. Once the pending submission is reconciled, changed inputs get a new ID and require a fresh preview. Include a browser test that loses a committed issue response and verifies retry returns the same invoice and reconciles history.

## Validation and calculation

Require an existing tenant company, language en/fi/sv, complete billing street/postal code/city/country (trimmed, maximum 250 characters each), and 1–100 rows. Descriptions are trimmed, nonempty, maximum 1,000 characters. Quantities must be positive, at most 10,000, with at most two decimal places. Unit net prices must be 0–1,000,000 EUR with at most two decimals, matching existing rate policy. Require a positive final gross total; individual free rows are allowed. Validate configured VAT with the existing 0–50 percent/two-decimal policy and payment terms 0–120 days. Reject malformed/null rows and invalid submission identifiers with validation errors. Enforce bounds server-side and mirror useful constraints in the UI.

Use .NET decimal. For each row round quantity × unit price to two decimals, MidpointRounding.AwayFromZero; round row net × configured VAT / 100 the same way. Sum rounded row net and VAT for invoice totals. Preserve row order and entered descriptions. Assign the configured VAT rate to every row. Use tenant-local today for issue date and saved payment terms for due date. Issuance rejects stale preview with 409. Missing company uses existing not-found handling; other invalid inputs use existing validation errors. Authorization follows the current admin invoice policy and tenant isolation.

## Verification

User clarification: manual invoices must use the company's existing invoice-reference sequence. Reuse the exact shared yearly invoice counter and existing payment-reference check-digit function; never introduce a manual counter or prefix. Cover alternating manual and shift issuance in the database test, including the resulting payment references.

Backend tests cover exact rounding, multiple rows, fractional quantities, zero-priced rows, invalid and oversized input, company lookup/isolation, stale previews after issuer/customer changes, deterministic preview, tenant-local dates, issuer validation, unchanged snapshots, shared numbering and payment references, and same/different-payload submission retries including paid/voided invoices. Verify concurrent same-ID issues produce one invoice with the existing reservation and transactional persistence pattern. Test manual invoices do not block shift billing. Check endpoint admin denial and normal invoice lifecycle.

PDF tests cover manual row descriptions/quantities/prices, VAT totals, existing issuer and customer details, no shift metadata, long/multipage rows, languages and applicable existing payment barcode behavior. Desktop/mobile browser tests cover mode switching, row add/remove, required input, preview and invalidation, stale response handling, issue/list/download, retry/error preservation and existing shift/partner flow regression. Run focused tests, frontend type/build checks, then required repository CI before delivery. Do not issue real production invoices during verification.
