# C03 customer workspace design (issue #137, part 1 of 2)

Date: 2026-11-04. Baseline: main `93753c4f` (PR #274). Depends on C02 (PR #257, merged).

## Split decision

Issue #137 covers two independent pieces. They ship as two sequential PRs under the same issue:

1. **PR 1 (this design): customer workspace.** Plan chunk C03. Read-only workspace over existing data, shared context links, lazy tabs.
2. **PR 2 (later, same issue): agreement service metadata, renewal/amendment lineage, expiry filters and alerts.** New data model. Not in this PR.

Reason: the metadata half adds nullable document fields, lineage and concurrency guards. Mixing it into the workspace would make one PR too large and hard to review.

## Options considered

- Dynamic route `/admin/companies/[id]`: rejected. The site is a static export (`output: 'export'`, 47 pages), so dynamic segments need `generateStaticParams`.
- Query state on the existing companies list page (`?customer=&section=`): rejected. The list already owns its URL state (status/page/size/q/company) and `applyParams`/`replaceUrlNext` logic. Adding a second mode would tangle Back/replace behaviour.
- **Chosen: separate static route `/admin/companies/customer/?id=<guid>&section=<tab>&back=<list query>`.** The list keeps its own URL state. Opening a customer pushes a history entry, so browser Back restores the list exactly. The `back` parameter rebuilds the list URL for the "Back to customers" link when the workspace was opened directly.

Current vs upcoming shift classification is deferred. It needs the tenant timezone and a date rule. This PR uses the existing Active/Inactive lifecycle split and shows validity dates.

## Roles

Companies, shifts, agreements and invoices admin endpoints all require the `admin` policy. There is no manager companies page. The workspace is admin-only. Manager access is out of scope. The issue's "tenant admin/manager" line is therefore not met by this PR. Record it in the PR.

## Backend

- `ListAgreementSummariesQuery(Guid? CompanyId)`: new query and handler (`ICompanyRepository` for names). The existing `ListAgreementsQuery` and handler stay unchanged because `AgreementDeleteTests` uses them. The controller list action sends the new query. Response adds `CompanyId` and `CompanyName`. A missing company is named "Unknown customer" and never throws.
- `ListInvoicesQuery(string? Status, DateTime? FromUtc, Guid? CompanyId = null)`: trailing optional parameter keeps existing constructors valid. Handler filters in memory after the repository list. Shortcut: in-memory filter, acceptable at current tenant size; upgrade to a repository filter if invoice counts grow.
- Controller list actions gain optional `companyId` query parameters. Cross-tenant ids return empty lists (Marten tenant scope) and `GET companies/{id}` returns 404.

## Frontend

- Companies list: each row gets an "Open" link to the workspace carrying the current list query as `back`. Existing behaviour is otherwise unchanged. Page title and nav label stay "Companies". The plan asked for a "Customers" label. Renaming it would break existing heading assertions in `admin.spec.ts` and `lifecycle-admin-theme.spec.ts`, so the rename is deferred. The menu group is already "Customers".
- Agreements and shifts pages read `?company=` on mount to preselect the company for create. Existing edit and create flows are unchanged.

## Assumptions

- A1: The admin-only policy is correct for C03 (no manager companies page exists).
- A2: Opening a customer pushes history. Tab changes push history too, so Back steps through tabs.
- A3: Shared context links are query-based, not client state, so a reload keeps the preselected company.
- A4: `adminGet(..., false)` for lists that change after mutations (agreements, shifts, invoices), per repo rule.
