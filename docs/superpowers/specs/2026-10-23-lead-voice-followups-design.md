# Lead voice notes and follow-ups

Date: 2026-10-23

## Scope and decisions

Extend the released Leads feature with in-app voice recording and persistent email follow-ups. The user confirmed access is for tenant admins and managers, never employees. No inbox history, transcription, AI processing, public audio links, or audio file-picker/upload UI. Recorded audio still requires a private authenticated HTTP transfer to the server when saved; it remains stored in the application.

Use the existing Marten/PostgreSQL persistence, private upload volume and Resend service. Browser timers cannot reliably send reminders after the app closes; a separate scheduling service adds infrastructure without a current requirement. Implement recording and reminder delivery as separate services sharing the lead lifecycle boundary.

Proposed defaults for review: five minutes and 20 MiB maximum per recording; once, daily, weekly or monthly reminders with a configurable interval; 06:00 in the tenant timezone. No customer-facing emails are sent by this feature.

## Access and UI integration

Tenant admins retain existing full Leads management. Managers can view/search Leads and private attachments, record voice notes, and create/edit/cancel follow-ups, choosing recipients from eligible tenant admins. Managers cannot convert, delete, deactivate/reactivate, or edit the company/branch/contact metadata of a lead in this increment. Selecting existing notification recipients does not grant permission to administer user accounts or change their emails.

Reuse a shared lead workspace in `/admin/leads/` and a dedicated `/manager/leads/` route linked from the manager workspace. Do not open the entire admin layout to managers. Capability checks hide unavailable actions; the server independently enforces them. Existing image create/delete and lead mutation routes remain admin-only; read routes may allow both verified roles. Require the existing verified active tenant staff identity where applicable; a stale manager token does not override an inactive or conflicting local employee binding. Tenant identity comes from authenticated context. Foreign IDs and private files return 404; anonymous, employee and platform-only credentials cannot access this feature.

Lead detail adds Voice notes and Follow-ups sections. The voice list shows the recorder's server-resolved name, recording date/time in tenant timezone, duration and an audio player. Preserve author-name snapshots if someone later changes their name or leaves; never accept an author name or subject ID from the request as authoritative. Follow-ups show reason, next date, 06:00 timezone label, recurrence, recipients and delivery status. Use paginated history, initially 25 items per section, so recordings and deliveries do not enlarge every lead list response.

## Recording and storage

Flow: Record -> microphone permission -> live timer and Stop -> preview playback -> Save or Discard. Auto-stop at five minutes. Stopping releases all microphone tracks. Leaving the lead or closing the dialog with an unsaved recording asks whether to discard it and always releases the microphone and object URLs. Recording does not start automatically. Keep the stopped recording in memory if saving fails and offer Retry without asking the user to re-record; a reload cannot recover an unsaved recording and must not claim it can.

Detect recording support and a compatible audio format at runtime: Opus/WebM, AAC/MP4 or Opus/Ogg according to browser support. Unsupported browser, denied permission, missing microphone and interrupted recording produce actionable messages without offering file upload. Test supported desktop Chromium and mobile devices, including Safari recording format through an appropriate browser/device check before release.

Use generated recording IDs and private tenant/lead paths outside public upload routes. The server enforces size, audio-only supported container/codec, actual readable media content and duration using an isolated bounded media probe (ffprobe packaged in the API runtime, argument-list invocation with generated paths, timeout and cleanup). Reject malformed, empty, oversized, video-containing and unsupported recordings. Client MIME and duration are hints only. The API cannot prove audio originated from the UI, so it enforces valid media and authorization rather than promising recording provenance.

Store metadata in a conjoined-tenant LeadVoiceNote document: ID, lead ID, creator subject, display-name snapshot, created UTC, duration, content type, generated storage key and version. Audio bytes stay on the private volume. An idempotent client recording ID scoped to tenant and lead prevents duplicate notes when Save is retried after an uncertain response. Same ID with different content is a conflict. Serialize save and lifecycle changes with the existing per-lead reservation and recheck eligibility before commit. Saving on an inactive, Lost or converted lead is blocked; saved audio stays readable to authorized users after closure/conversion.

Authenticated playback checks lead membership and note ownership, returns the canonical audio content type with no-store/nosniff, and supports seeking via byte ranges (or authenticated complete-blob playback with object-URL cleanup). No audio bytes or signed public URLs appear in list responses. Admins can delete a voice note after confirmation; managers cannot delete saved notes in this increment. Converted leads are fully read-only, including admin deletion of existing voice notes. Commit metadata removal before idempotent file cleanup. Deleting an eligible lead removes note metadata and schedules private-file cleanup; conversion retains recordings on the historical lead without copying or exposing them on a public customer page. A bounded maintenance sweep recovers unreferenced generated audio files older than 24 hours after crashes; take the lead reservation, recheck metadata and pending saves, and remove only verified private audio paths. Never remove a file referenced by current metadata.

## Follow-up definitions and lifecycle

A lead can have several independent follow-ups. Each has a required reason (maximum 1,000 characters), first local calendar date, fixed local time 06:00, recurrence (once/daily/weekly/monthly), interval 1-365, optional inclusive end date, selected active tenant-admin IDs, creator/updater identity, version and state. Require 1-20 distinct recipients with valid email addresses. An inclusive end date must be on or after the first date; validate calendar bounds before recurrence arithmetic so invalid or overflowing schedules return a validation error. Resolve eligible admins through the authoritative tenant identity directory, including admins who have no employee row; exclude disabled users and any local inactive/conflicting binding. Recipient IDs are tenant users, not arbitrary email strings, customer contacts or employee IDs. Directory failures block scheduling with a clear retry message instead of silently accepting unchecked recipients.

Default the first date to the next local day; a user may choose today. If today's 06:00 has passed, explicitly show that it is due now and enqueue it after save. Reject dates before today when creating/editing the next schedule. A once reminder completes after delivery processing; recurrence continues until the end date or cancellation/lead closure. Monthly schedules retain the original day and clamp to the last day of shorter months without drifting: January 31 -> February 28/29 -> March 31. Daily/weekly dates advance by local calendar dates rather than 24-hour UTC increments.

Use the existing Lost status as closed; deactivation also stops reminders. Conversion, setting Lost, or deactivation atomically cancels pending follow-ups and unsent deliveries under the lead reservation. Reactivation or changing Lost back to another status does not restart old schedules automatically. Users must explicitly create a new follow-up. Manual cancellation is immediate for pending work and preserves history. Converted leads are read-only for new notes and schedules.

Follow-up edits use expected versions. Editing reason, recipients or dates supersedes pending unsent occurrences with a new schedule revision; sent delivery history is immutable. Cancellation and dispatch use the same per-lead reservation. If a send has already started, it may complete before cancellation returns; once cancellation returns, no additional send may start. Do not claim an already accepted email can be recalled. The UI reports this behavior and never silently restarts a cancelled schedule on refresh.

## Durable scheduler and delivery

Persist LeadFollowUp definitions and per-occurrence/per-recipient LeadFollowUpDelivery records as conjoined-tenant documents. A background worker scans active registered tenants roughly once per minute, computes due dates using the tenant profile timezone and uses database claims/leases to tolerate multiple replicas. Start-up also scans due work. 06:00 is the scheduled time, not a guarantee of exact email arrival. Show scheduled and actual send times.

For timezone changes, use the current tenant timezone for unclaimed future occurrences; materialized deliveries retain their original local date, timezone and due UTC. Delivery identity includes follow-up ID, schedule revision, local occurrence date and recipient ID, preventing repeats when the UTC offset changes. For nonexistent local times advance to the first valid instant; for ambiguous times select the first occurrence and send once. Check due work, lead state and recipient eligibility again immediately before dispatch.

After downtime, send at most the latest overdue occurrence of each recurring schedule and mark earlier missed occurrences skipped, then advance to the next future local date; send an overdue one-off once. If the optional end date has already passed in the tenant timezone, skip unsent past slots and complete the schedule instead of sending stale catch-up emails. A durable slot/recipient uniqueness constraint, transactionally advanced schedule and lease recovery prevent overlapping workers from duplicating logical deliveries. Never send for inactive/suspended tenants. A recipient who is no longer an active admin is skipped with a visible reason. An eligibility-directory outage is retryable: defer delivery without treating users as ineligible or sending against stale authorization. Other eligible recipients still receive their own emails; addresses are not exposed to each other.

Send branded HTML containing lead name, follow-up reason, due date/time/timezone, recurrence summary and an authenticated Open lead button. Escape entered text; include no recording attachment or public link. Record provider acceptance separately from delivery-to-inbox: UI says Sent when Resend accepts it, not Delivered unless later confirmed by a webhook (outside this scope). Missing Resend configuration is an error, not a successful no-op; preserve existing unrelated email callers while introducing a strict reminder-send contract.

Persist an immutable payload snapshot and a stable Resend idempotency key per slot/recipient before making the request. Retry transient/network/429/5xx failures using bounded backoff and Retry-After where available. Stop automatic attempts within 20 hours of the first provider attempt, below Resend's documented 24-hour idempotency retention; permanent errors fail immediately. A crash after uncertain provider acceptance can reuse the same payload/key within that window. If that window expires without a confirmed outcome, mark delivery Needs review and do not automatically resend with a new key. An admin may explicitly send a new reminder, with the possibility of a prior accepted email clearly shown. Successful recipients are never resent when another recipient fails. A terminal failure does not cancel later recurring dates. Store safe errors/attempt counts without credentials or raw provider response bodies.

## Boundaries and API

Keep the existing LeadService for metadata/lifecycle/conversion; introduce LeadVoiceNoteService (author attribution, idempotent save, access, media validation and file store), LeadFollowUpService (definition validation, recurrence, recipients and lifecycle cancellation), and LeadFollowUpDispatcher (claims, immutable payloads, retries and Resend transport). Repositories share the tenant session and per-lead reservation for lifecycle transactions. Voice probe and email transport have injectable interfaces for deterministic tests. Cancellation on conversion must be part of the same transaction, not a best-effort callback after saving. Permanent deletion of an inactive unconverted lead transactionally removes its follow-up definitions, delivery history and voice-note metadata; the same lead reservation prevents dispatch during deletion, and private-file cleanup follows commit.

Add role-scoped list/detail, voice-note save/read/delete and follow-up create/update/cancel/history endpoints under a Leads collaboration resource accessible from both workspaces. Continue to protect the original metadata mutation/conversion/deletion endpoints as admin-only. The recipient lookup returns only eligible admin ID, name and email for the authenticated tenant. Use standard ProblemDetails, 409 for stale/conflicting requests, 413 for size limits and clear media/permission validation. Include capability flags in detail DTOs; never rely on them instead of server authorization. No public routes or external-user playback.

## Acceptance and verification

Backend and real PostgreSQL tests: admin/manager/employee/anonymous/platform audience and cross-tenant boundaries; author spoof rejection, disabled/conflicting identity handling, private byte isolation, valid and invalid audio probes, byte/duration caps and generated paths; retry idempotency, conflicting recording IDs, save-vs-close races and cleanup; all recurrence types, end dates, month-end/leap years, tenant timezone/DST/change behavior; once/today overdue behavior; restart/downtime coalescing; multiple independent follow-ups; stale edits, superseded occurrences, conversion/Lost/deactivation/manual-cancel races; two workers/lease expiry/unique delivery slots; per-recipient failures and eligibility changes; missing configuration; provider idempotency and uncertain-window expiry; no duplicate successful sends or false delivery status.

Playwright desktop/mobile: admin and manager navigation and allowed/denied actions; recorder start/stop/timer, preview/discard/save, permission denial, unsupported media, auto-stop, leave confirmation, microphone release and upload retry retaining audio; author/time/playback and admin deletion; converted history preservation; multiple follow-ups and reasons, recipient selection, dates/recurrence/end date, validation and stale-error preservation, edit/cancel/status/history; closed/converted/inactive disabled controls and no automatic reactivation. Use synthetic media and fake time/email transport in CI; separately verify a real microphone recording on a supported mobile browser and desktop without sending production reminder emails. Required build, typecheck, CI and review before merge/release.
